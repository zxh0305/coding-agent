# coding-agent 可靠性优化方案

调研日期为 2026-11-05。coding-agent 基线 8cf1d68；ZCode 本地基线 aac47556；DeepSeek Harness 本地基线 d743267388；mai_portal 本地基线 99669b01b。本文只交付调查与开发方案，不修改运行代码、业务数据库或运行中的服务。

## 1. 调查结论

优先补齐项目环境识别、规则加载、文件版本保护、同轮验证闭环和可比较的回归任务。MCP 接入主要增加外部能力；今天的慢任务主要使用已有读写和 shell 工具，未发现因缺少某个 MCP 而导致其无法完成核心代码操作的证据。

这并不证明现有 Agent 和其他产品在同模型下同样可靠。尚未进行同任务、同模型、同起始代码的对照运行，也未核验模型服务端实际映射。因此以下建议依据本地源码和实际运行证据，性能改善需由回归实验确认。

## 2. 真实任务还原

定位到一轮 51 次模型请求、约 269.5 秒的开发任务。用户要求实现接口需求、测试、不影响其他功能，并提供数据库变更。

该轮 55 次工具调用包括 read_file 13 次、run_bash 17 次、grep 1 次、todo_write 4 次、apply_patch 18 次、write_file 2 次。13 次 read_file 的文件与分页参数没有完全重复。修改覆盖六个文件，其中 SQL 六次、模型五次、服务五次。17 条 shell 命令中有 11 条包含 sed 或 grep 读取；检查命令中识别到两次 AST 校验、四次提取函数或替换依赖的脚本。这些标记可重叠，只用于描述验证方式。

这轮不应简单归因为死循环。工作本身涉及多个入口，且存在实质修改。改进空间在于 shell 读取绕开专用工具的观察机制、零散修改增加请求次数、验证层级不足。

最终回复明确披露“接口未实际运行”，也说明了静态检查和局部逻辑测试。因此没有证据据此指控它伪造了接口测试。但用户要求上线前验证，现有证据尚不足以支撑真实运行和兼容性结论。

最终回复称本机没有 Flask/SQLAlchemy。只读检查发现项目同时有 venv 和 .venv，.venv 的 site-packages 中存在这两个包的安装元数据。包目录存在不等于解释器必然能导入，不过值得优先验证，不能检查系统 python3 后就宣称整个项目缺少依赖。

另一次配置调查用了 20 轮、约 85 秒，日志统计模型耗时约 83.4 秒、工具约 0.7 秒。这个案例增加模型往返的代价远大于文件读取本身。工具耗时相加与墙钟不是所有并行任务都能直接相减，不能据此推导所有任务的固定占比。

## 3. 源码比较中值得借鉴的做法

### ZCode

- core/src/runtime/methods/context.ts 从会话目录解析上下文来源；context/sections/request-user-context.ts 将来源明确的项目指令纳入请求。值得借的是可追溯的项目规则，而非完整复制其上下文框架。
- core/src/tool/handlers/edit.ts 实际检查文件是否读过、读取版本是否过期，成功后更新观察状态，并告知模型不必无理由再次读取。当前 coding-agent 在工具描述中要求先读，但 write_file 和 apply_patch 没有对应的会话读取版本闸门。
- core/src/runtime/methods/turn-loop.ts 在每轮准备工具列表，并有上下文整理与输出延续逻辑。不能把这些单独视为“任务一定正确”的保证。

以上路径均相对 ZCode/apps/zcode-cli/packages。

### DeepSeek Harness

- packages/context/agent-instructions/src/index.ts 与 files.ts 负责首请求基线、涉及更深目录后的规则补充、恢复时对账。README 与代码说明规则有字节预算、去重和路径边界，不必全库扫描。
- packages/fs/fs-observation-policy/src/index.ts 与 tool-fs/src/edit.ts 配合，区分未读取、版本变化、文件不存在等错误，给出重新读取的补救信息。该能力取决于部署是否加载相应 policy。
- packages/shell/tool-bash 的命令结果保留退出状态，由模型解释普通非零退出；可组合后台 job 来处理长命令。当前 coding-agent 将所有非零退出统一记为 ok:false，需要区分“命令正常运行并返回非零”与执行器或权限错误。
- packages/core/agent-loop/src/tool-calls.ts 在取消时停止启动新调用，处理已启动调用，并补齐缺失结果，维护可回放的调用与结果配对。当前项目已有只读并行、写串行、取消机制，应补契约用例并复用。

### mai_portal

实际参考位于 ../company/mai_portal；直接上层的 ../mai_portal 只有文档。

- job/comm/assistant_agent_builder.py 组装 Claude Agent SDK 运行时，组合系统提示、场景知识、主代理与成员工具和模型。部分可靠性来自 SDK 的现成执行能力，不能将其等同于自己编写的通用循环。
- job/comm/unified_tool_loader.py 按服务、会话、场景和产出类型裁剪工具，并保留来源及缓存。值得迁移的是“当前任务需要什么就提供什么”，而非一次增加所有业务 MCP。
- job/test_job/test_script/api_test_agents/script_gate.py 有排除恒真断言、诊断脚本冒充业务测试的设计；runner.py 使用试跑停止条件。此处仅确认 gate 实现及部分 runner 接线，未证明所有测试链路都执行了所有 gate。
- 项目 AGENTS.md 包含跨数据库、桌面/Web、启停与生产操作规则。coding-agent 当前缺少统一读取并注入该正文的入口，这会让模型错过已有约定。

## 4. 建议的目标行为

接到任务时先确认项目、分支、解释器及项目规则。模型先确定本轮要交付什么和怎样验证，再进行必要调查和修改。修改工具核对读取版本。准备最终回答时宿主执行已配置的验证；失败证据回给同一回合，允许有界修复，再生成最终回答。最终展示实际做过的检查、未覆盖部分和剩余阻塞。

小问题可以直接答；查询任务不要求创建计划；用户停止立即收尾。涉及外部服务、安装依赖、发布或真实数据库变更时，遵守现有权限和用户授权范围。

## 5. 分阶段实施

### 第一批 · 让 Agent 在正确的环境里工作

提交 A，项目规则加载。

在 backend/services 新增小型规则解析模块，接入 Agent 的实际模型上下文入口。先实现当前项目根 AGENTS.md 与 CLAUDE.md 的明确优先级、内容去重、大小上限和来源路径；后续支持触及子目录后的增量规则。范围止于已选择的项目根，避免把旁边仓库的规则带进来。

规则与技能分别记录。规则长期描述项目约定；技能仍按已选择版本注入；记忆用于补充背景，不能覆盖本轮用户指示。普通文件内容或工具输出无法自行升级为系统权限。上下文裁剪不能悄悄吞掉规则，无法读取或超限须显示诊断。

验收包括首次提问、项目切换、压缩后恢复、规则修改、嵌套路径、越界软链接和重复文件。确认修改代码或执行命令前模型确实收到有效规则。

提交 B，项目环境卡。

扫描有限的标记文件和候选解释器，读取启动脚本中的约定，识别 .venv/venv、包管理器锁文件、项目测试入口。仅发现元数据，不能直接导入任意项目模块；用户确认或按权限执行的探测才产生“可用”结论。记录解释器绝对路径、cwd、探测时间及结果。

模型调用 shell 时采用项目确认的环境。对“系统 Python 无模块但项目 .venv 可用”返回具体补救提示；环境不完整时保留阻塞证据。无需每轮激活环境或重复扫描，也不自动安装依赖。只改 cwd 不等于选择了 Python 环境。

验收包含两个虚拟环境、依赖缺失、解释器失效、项目迁移、Node 与纯 Python 仓库。真实项目只做只读环境识别，执行验证用隔离样例。

### 第二批 · 保护修改，并缩短无效往返

提交 C，文件观察状态。

read_file 返回或登记规范路径和内容指纹；write_file 覆盖已有文件、apply_patch 修改前核验观察状态。文件被外部编辑后拒绝旧写入并明确提示重读。新建文件防止覆盖刚出现的同名文件。工具修改成功后更新观察状态，减少改后立即重复读取。

现有工具参数尽量保持兼容，观察状态由服务端会话维护。grep 命中片段不等于读过完整文件。shell 中读取文件不能通过脆弱正则自动证明完整读取；优先引导使用 read_file，shell 改文件也不能被误认为全部受版本保护。文件锁只能约束合作方，核验与替换之间的外部写入窗口须明确测试并说明限制。

验收重点是多标签页、用户同时编辑、部分文件读取、恢复旧会话、文件删除重建与补丁匹配失败。原子写入仅防止半文件，不可替代版本核验。

提交 D，结构化工具结果和进度判断。

保持旧 ok/error 接口兼容，增加明确的错误类别和运行状态，例如执行器失败、权限拒绝、超时、正常退出及 exit_code。grep 无匹配和 git diff 有差异需要按命令意义解释，不能统一诱导模型“修复工具错误”。未知复合 shell 命令保留原始状态，避免草率判断成功。

替换 agent.py 中“非只读且返回字符串不含 error 就算有进展”的续轮判定。run_bash、todo_write 成功不能自动证明代码任务有进展；结合受控修改记录、检查结果变化以及待办完成证据判断。窗口内观察跨工具的相同错误和相同文件版本，给具体改道提示，保留合理的复验。

首版把建议变成提示与诊断，先收集误报，再启用严格限制。长任务按交付物推进，不为降低轮数强行打断，也不在每轮插入一大段计划。

### 第三批 · 完成同轮验证与修复

提交 E，最终回答前的验证边界。

当前 services/turn.py 在 agent.run 已发出最终 done 后执行 verify.run，结果进历史后当前回合结束。现有失败卡和继续修复按钮使证据可见，但不会让模型在同一回合看到失败后再作最终结论。

将“模型准备收尾”设为一个显式边界。宿主先执行本项目配置的检查，通过后再生成最终答案；失败时将证据交给模型继续修复。默认最多两次修复尝试，并设总时长和调用预算；超限、环境缺失、权限未获批、用户停止时输出当前结果与阻塞。预算值可由实验调整。

执行仍通过统一权限与执行器，传递取消信号。沿用 verify.py 的发现逻辑，但命令白名单只是一层筛选，不替代正常授权。上次检查后工作区没有变化则复用结果；变更涉及不明依赖时保守重验。用户已要求仅调查时不启动写入或修复。

检查结果记录命令、cwd、解释器、退出状态、耗时、作用范围、被测文件版本。已有工具输出可供提取事实，但“模型说通过”不能产生通过记录。抽取函数和 mock 测试可以报告局部结果；路由、ORM、真实服务行为仍需正常入口的测试。启发式识别只能提示证据不足，不能证明有 expect 的测试就可靠。

结果状态分开表达“流程结束”“检查通过”“存在失败”“验证不足”。没有对应集成证据时，界面不产生“可上线”结论。普通问答只显示正常回答。

### 第四批 · 提升对话连续性和按需工具

提交 F，长任务的简短状态与上下文保存。

输入框附近显示当前项目、正在用的规则/技能和执行阶段。长任务只在阶段变化或关键发现时提示，显示“识别环境”“修改文件”“等待检查”“检查失败后修复”等事实。后台真实在跑检查时不能显示已完成。

压缩摘要固定保存本轮目标、用户明确约束、改动文件、未通过命令、环境阻塞和下一步。保留证据引用及待办状态，不将输出中的建议当作用户授权。用户追问“继续”“现在呢”时沿当前目标接续。

提交 G，工具按需开放。

先复用已有读写、搜索、shell、浏览器、文档、子代理。把项目规则与任务类型对应的工具做成小型能力配置。只有实际出现外部系统需求时接入对应 MCP，例如用户要查某个 GitHub Issue 或读取设计稿。记录连接状态、可用工具和项目启用范围，隔离鉴权失败。

先用同一模型比较工具清单大小是否影响选择正确性。不要因“更多”就假设更强，也不要把按需裁剪错误做成缺工具。当前可用工具诊断要可查看，用户显式请求的能力应可恢复。

## 6. 如何证明改善

准备 8～12 个隔离的真实任务样例，每项定义正常入口验收与应保持的旧行为，覆盖下面的案例。

- 简单定位问题，检查不扩大修改。
- 修复现有路由缺陷，运行真实测试客户端。
- 两个虚拟环境中选对解释器。
- 文件被用户改动后拒绝旧版本覆盖。
- grep 无匹配后正常继续调查。
- 首次检查失败后同轮修复并重新运行。
- 数据库不可达时明确阻塞，不能拿 mock 结果冒充集成通过。
- 长任务遇到中断、压缩或恢复后保留原始目标。
- 不同项目的规则、技能、工具与会话状态互不串用。

固定模型标识、供应商、参数、仓库起点、项目约定和权限，记录实际模型响应标识；使用同一提示，至少重复三次。模型执行有波动，单次成功不能代表改善。每次在独立副本运行，不复用上次产物；旧基线与新实现使用同样的测试夹具。

主要指标是正常入口任务通过率、无证据完成声明次数、误改已有代码次数。辅以人工追问次数、首次发现环境问题的时间、轮数、耗时、token 和失败后的恢复次数。性能数字是基线对照结果，不预先承诺降低固定百分比。

先对比 coding-agent 改造前后，再在可配置相同模型、相同权限的条件下对比其他产品。若模型或服务端提示不可控，报告比较限制。现有 810 个后端单测和前端/浏览器回归用于防代码回归，还不能替代这些真实 Agent 任务样例。

## 7. 推荐交付顺序

先做 A 与 B，解决不知道项目约定、用错运行环境的问题。接着 C 保护用户正在编辑的文件。随后 E 把验证结果送回当前回合，并完善结果状态。D 根据真实回合数据逐步收紧，F 配合 E 改善等待和接续体验，G 按实际外部能力需求增加。

每项独立中文提交，使用临时库、临时项目和固定任务验收。无需整体替换框架。优先完成可观察、可验证的行为，再决定是否更换模型或增加 MCP。
