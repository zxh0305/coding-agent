# coding-agent 可靠性改造开发方案

设计稿 v1，2026-11-05，基线提交 8cf1d68。本文中的模块、接口、字段和默认值为拟定设计，尚未实施。配套证据见 agent-reliability-plan-2026-11-05.md。

## 1. 目标和完成标准

接到项目编码任务后，Agent 应加载项目约定、识别运行环境、保护用户正在编辑的文件，并在授权范围内通过正常入口验证。失败证据返回当前回合继续修复，最终交付实际结果和未覆盖部分。

可靠性以任务通过率、已有功能兼容性、误改次数、无证据完成声明及需要用户追问的次数衡量。耗时、轮数和 token 作为辅助指标，不能通过少做验证换取数字下降。

首版覆盖本机 Python/Node 项目。保持 Python 标准库、SQLite 和原生前端，复用现有权限、执行器、消息回执、技能、差异、上下文和实验记录能力。

## 2. 已确认的问题

- 项目规则正文没有统一加载入口，现有 AGENTS.md 读取主要用于发现验证命令。
- 一轮任务称缺 Flask/SQLAlchemy，但项目 .venv 存在安装元数据。需要先识别并探测项目解释器，再判断环境是否可用。
- write_file/apply_patch 有原子写与匹配检查，缺少会话读取版本核验，无法完整防止旧内容覆盖外部修改。
- verify.run 在 Agent 已发最终 done 后运行，失败结果进入下一次请求，尚不能驱动当前回合修复。
- 非只读工具成功可被算作续轮进展，更新待办、零退出 shell 命令不一定代表交付物有推进。
- 现有检查卡能展示失败，但流程正常结束与任务验收完成还需要独立表达。

51 轮案例有真实修改，也明确披露接口未运行。因此优化应提升环境识别、验证覆盖与执行机制，不能据轮数断言它一直死循环或伪造了接口测试。

## 4. 目标执行流程

1. 接收消息，沿用归属、工作区、技能版本与 nonce 幂等检查。
2. 创建本轮 user_mid，保存项目规则和环境上下文快照。
3. 调查、调用工具和修改文件，小问题可直接回答。
4. 模型产生无工具调用的候选回复，进入准备收尾节点。
5. 编码任务根据配置选择检查，经过权限判断后执行。
6. 失败且有修复预算时，把实际证据回填给同一 Agent，继续修复和重跑。
7. 通过、阻塞、预算耗尽或用户停止后确定最终回复。
8. 保存结果、检查与差异，再发送 turn_end 推进队列。

检查通过只证明声明范围内的检查成功；“可上线”仍需要对应环境和集成证据。

## 5. 项目规则和环境

### 5.1 规则发现

首个提交支持项目根 AGENTS.md 与 CLAUDE.md，按明确顺序呈现，内容相同只保留一份。后续支持对实际触及文件加载项目根至文件目录的规则链。范围止于选中的项目根，不扫描旁边仓库。

每份规则记录路径、SHA256、读取时间、完整性和诊断。建议总预算 32 KiB、单文件上限 128 KiB，后续根据实验调整。优先保留具体目录规则，无法读取和超限必须显示诊断，不能伪装成文件不存在。

系统约束、项目规则、本轮任务、所选技能和背景记忆保留各自来源。记忆与工具输出不能升级权限。用户本轮明确要求优先于项目一般默认习惯，冲突必须保留来源并说明处理结果。

根规则在回合开始时加载，触及子目录后增量补充，规则变动在下一次模型请求前更新。旧回合快照保持原始版本。压缩不能重复注入或悄悄丢掉有效规则。

Web、CLI 和子代理复用同一解析模块。子代理只继承其任务范围需要的规则，工具权限保持原有边界。

### 5.2 环境识别

有限扫描 .venv、venv、pyproject.toml、requirements、package.json 和锁文件。区分 discovered、usable、unavailable，包目录存在只能证明 discovered。经许可完成解释器和依赖探测后才可标记 usable。

多个候选环境优先使用项目明确配置；无法确定时展示候选让用户选择。扫描不执行任意项目模块，不自动安装依赖，也不把 .env 的值注入模型。环境缓存按配置和解释器版本失效。

新增可选 .agents/project.json，仅在用户保存设置时创建。建议字段为 schema_version、runtime、checks、repair。runtime 指定项目内解释器或包管理器路径；checks 包含 id、argv、相对 cwd、超时、声明层级和适用路径；repair 保存尝试次数与时间预算。

个人模型和授权偏好继续放 SQLite，项目配置不存密钥或自带“已批准”标记。项目文件中的检查命令都作为待授权输入处理。

Python 检查编译为解释器绝对路径加 -m pytest 等 argv。普通 shell 向模型提供已确认的环境，避免每次重新猜测。不对任意 shell 文本作简单 python3 替换。

拟定配置示例，路径和命令需按实际项目选择，不能直接当作 mai_portal 的运行配置。

```json
{
  "schema_version": 1,
  "runtime": {"type": "python", "executable": ".venv/bin/python"},
  "checks": [
    {
      "id": "unit",
      "argv": ["{python}", "-m", "pytest", "tests/unit", "-q"],
      "cwd": ".",
      "timeout_seconds": 300,
      "level": "unit",
      "paths": ["backend/**", "tests/**"]
    }
  ],
  "repair": {"enabled": true, "max_attempts": 2, "total_timeout_seconds": 600}
}
```

只支持定义好的 {python} 占位符，不能执行任意插值。argv 通过结构化执行入口传递；需要兼容 shell 执行器时使用平台正确引用规则，权限检查与实际执行必须基于同一份已解析命令。配置错误阻止该项检查并保留原配置，不回退成另一个模型猜测的命令。

## 6. 文件版本保护

ToolContext 增加按会话管理的观察状态，记录规范路径、内容指纹和读取范围。read_file 登记观察，apply_patch 修改前核验当前版本。已有文件的整文件 write_file 需要完整读取或明确的替换确认；新文件采用排他创建。

错误类型包括 FS_NOT_OBSERVED、FS_STALE_VERSION、FS_NOT_FOUND、FS_NON_UNIQUE_MATCH，提供对应补救。成功修改后更新观察状态，返回简短差异和新版本，避免无理由再读一遍。

文件级锁约束本服务内的并发修改，临时文件替换继续防止半文件。外部编辑器不遵守服务锁，提交前重验可缩小冲突窗口，但不能承诺跨进程强事务保证。无法确认安全提交时拒绝旧修改，保留用户文件。

shell、格式化器和测试可能修改文件，下一次专用写入仍须重验。不能用正则识别 cat 就假设读过完整文件。Agent 恢复后重新建立观察，旧历史行号不是当前版本证明。

## 7. 工具结果和进度

保留现有 ok/error/hint 的兼容性，增加 outcome、error_code 和结构化执行状态。区分正常退出、执行器故障、权限拒绝、超时和取消。普通非零退出保留 exit_code，由命令语义解释；先迁移调用方，再调整旧成功判定。

grep 无匹配和 git diff 有差异不应统一诱导“修复工具错误”。复杂命令无法可靠分类时保留原始证据，不用末尾 echo 的零退出证明前面的测试成功。长输出沿用全文引用，摘要优先呈现关键错误。

继续只读并行、修改串行。取消后不派发新工具，已启动工具收尾，并为未启动调用补齐取消结果以保持合法消息序列。

用实际修改记录、检查结果变化和证据变化辅助判断进展。todo_write 成功或 shell 零退出不能单独续轮。首版只发无进展提示，观察最近 6 次调用的参数、文件版本、结果指纹；合理复验与等待任务排除误报。阈值经真实实验校准后再决定是否严格限流。

## 8. 同轮验证与修复

### 8.1 Agent 内的接入点

在 agent.py 增加可选 completion_policy，由当前 _run 在无 tool_calls、调用 _tail_answer 前驱动。策略结果为 accept、continue_with_feedback 或 blocked，默认未注入时沿用旧行为。

Web 由 session_boot 注入项目验证策略，CLI 复用策略并使用其权限交互。不能等 Agent.run 退出再套一轮修复，因为现有 finally 会设置取消信号，压缩和回合生命周期也已经结束。

候选回复可进入历史作为尚未验收的助手输出，检查反馈使用宿主控制消息，维护合法 assistant/tool 配对。反馈不能伪造用户授权。

### 8.2 流式与事件契约

完成前的正文显示为过程段或待确认回复；准备收尾时显示“运行检查”。最终 accept 只发一次 done，turn_end 仍是队列推进的唯一信号。修复中不能出现多张正式最终回复。

新增 turn_phase，包含 user_mid、phase、attempt。phase 支持 preparing、working、verifying、repairing、finalizing。新增 check_update，包含 check_id、状态和摘要。沿用现有 SSE seq、回放和视图版本守卫。

先补事件契约测试，再修改展示，重点覆盖候选回复、最后一帧推理、断线补发和多次修复。

### 8.3 检查选择与执行

优先显式项目检查，其次复用 verify.discover。用户要求完整测试时不被路径筛选缩小范围。依赖关系未知时保守验证，不把没有匹配到配置解释成已验证。

所有检查使用同一权限闸门、执行器和取消信号。命令发现白名单不能证明 make test 或 npm test 没有副作用。未知项目检查继续遵守既有授权策略。

检查记录 argv、cwd、解释器、开始和结束时的代码版本。检查期间代码变动则标为 stale，不把通过结果归给新版本。仅当代码和环境均匹配时复用旧结果。

初始预算建议最多两次修复、总验证十分钟，单命令默认五分钟且受总预算约束。修复请求计入原回合调用和轮数限制，不能绕开原上限。预算可在项目设置中显式调整。

### 8.4 结局

| 情况 | 行为 |
| --- | --- |
| 已配置检查通过且有效 | 生成实际验证结论 |
| 检查失败、有预算和授权 | 同轮回填证据，继续修复和重跑 |
| 缺依赖、服务不可用、权限拒绝 | blocked，说明需要的条件 |
| 修复预算耗尽 | failed 或 insufficient，展示最后结果 |
| 用户停止 | cancelled，停止进程组且不启动后续工作 |
| 没有检查配置 | insufficient，带验证限制交付 |
| 纯问答和只读调查 | not_applicable，不增加空卡 |
| 服务重启 | 未完成执行 interrupted，不自动重跑可能已经生效的写操作 |

session_turns 的现有执行 state 保留，新增 assessment 表达验收状态。passed 仅表示声明范围的检查通过。syntax、unit、integration、browser 由配置声明并同时展示实际命令；抽取函数和 mock 结果不能认领真实接口集成通过。启发式检测只用于提示证据不足。

## 9. 数据结构与迁移

新增 turn_checks 表，每次检查用独立 check_id，关联 session_id 和 user_mid。

| 字段组 | 拟定内容 |
| --- | --- |
| 身份 | check_id、session_id、user_mid、check_key、attempt |
| 输入 | argv_json、cwd、runtime_json、input_fingerprint |
| 状态 | pending/running/passed/failed/blocked/cancelled/interrupted/stale |
| 输出 | exit_code、timed_out、started_at、ended_at、reason、output_ref、preview、truncated |
| 来源 | source_file、source_hash、declared_level |

检查开始前落库，结束后更新。输出复用数据区存储与分页读取，摘要有界。session_turns 增量增加 assessment、assessment_reason、phase、repair_attempts、context_ref，或等价的扩展元数据。

规则正文快照、环境摘要以 user_mid 关联到数据区，数据库存引用与哈希。归属校验覆盖会话、检查和输出路径。日志不打印密钥、认证头或完整环境变量。

运行中的检查不能借用临时 trace 行作为唯一存储，因为 _maybe_snapshot 会替换该行，收尾还会删除它。changes 可保存兼容摘要，新的检查表是持久化真相。

删除会话、回退截断和孤儿清理须同步处理新记录和输出。旧回合不从自然语言批量推导 passed。迁移编号在实现时取 MIGRATIONS 下一号，补探针、旧库升级、重复初始化和清理测试。

## 10. API 与交互

新增 GET /api/sessions/<sid>/checks，按 user_mid 返回摘要；GET /api/sessions/<sid>/checks/<check_id>/output 分页取输出。校验会话 owner 后再检查 check_id 归属。

历史消息返回 phase、assessment、checks 摘要。前端优先新结构，没有新数据时使用旧 changes.verification，避免重复卡片。先提交数据库再发事件；SSE 缓冲淘汰后仍可刷新恢复。

输入框附近只用一行显示阶段。“查看项目上下文”可查看规则来源、解释器、技能及检查配置。项目设置可选解释器、编辑检查；保存配置和执行授权分别处理。

改动卡显示实际通过数、失败数或阻塞；展开显示命令、范围、时长、版本和输出。沿用“继续修复”，不覆盖草稿。检查仍在运行时不能显示完成，切项目丢弃过期请求，桌面与窄屏均验收。

## 11. 长对话和上下文

压缩固定保留本轮目标、用户约束、项目/分支、修改文件、失败命令、环境阻塞与下一步；原始消息继续保存在库，输出保留引用。关键执行事实由宿主记录，不能只依赖模型自由总结。

规则、环境和技能分别计量上下文，稳定部分优先缓存。首次迭代不增加每轮额外规划模型调用。简单任务直接处理，长任务才用现有待办。

“继续”“现在呢”结合当前未完成目标和最新用户要求。用户切项目或明确换目标时重建上下文，旧检查结果不能认领新任务。

| 提交 | 交付物 | 完成条件 |

| 5 收尾策略 | 候选边界、一次最终 done | 同一 user_mid、无重复答案、可取消 |
| 6 同轮修复 | 权限、反馈、预算、重跑 | 失败后修复通过，阻塞和停止正确收尾 |
| 7 验收 UI | 阶段、范围、新旧兼容 | 桌面/手机、断线、刷新、草稿正常 |
| 8 进度与摘要 | 结构化错误、无进展提示、固定摘要 | 无效交替调用有提示，合法长任务不误停 |

1～3 是首批可交付版本，4～7 是同轮验证版本，8～9 是持续改进机制。预计 10～15 个有效开发日，含集成与回归；时间为工作量估计，取消、旧数据与工具兼容问题可能增加工期。

## 14. 测试和发布门槛

单元和接口覆盖规则范围、预算、环境、旧写拒绝、权限、取消、检查状态、重复提交、迁移和清理。前端覆盖仅一次 done、turn_end 推进队列、实时与历史一致。浏览器验证慢检查、修复、取消、断线、切项目和 320/390 宽度。

真实 Agent 首版十项样例覆盖问答、定位、Flask 路由修复、双虚拟环境、并发编辑、搜索无匹配、失败后修复、集成服务缺失、压缩和停止恢复。验收器通过程序正常入口判断，独立于模型答案。

先用模拟模型验证状态机，再做真实模型评估。复用实验记录组件，编码场景独立配置执行范围，不能把现有仅文件工具的 order_report 当作 shell 沙箱。每次在独立副本和隔离服务中运行，固定提示、供应商、返回模型标识、参数、起点、规则和权限，每项至少三次，保留失败记录和未知用量。

必须持续保持的状态不变式包括以下各项。
- 同一 nonce 的网络重试不新建第二个任务或第二次执行。
- 同轮修复沿用 user_mid，所有模型调用计入原预算。
- 回合未结束时 SSE 重连不能把 verifying 误判成已完成。
- 同一候选回复不能产生多个正式 done，队列只由 turn_end 推进。
- 检查结果的代码版本不匹配时不得显示为当前版本通过。
- 停止后排空已启动调用，未启动调用不再执行。
- 已经开始且可能有副作用的工作，不因重启被自动重做。
- 工具输出、规则文件和测试脚本均不能赋予额外操作权限。

轮数、时间、token 不预设必降比例，报告额外验证成本和实测收益。同模型对照 ZCode/DeepSeek Harness 时注明环境差异，模型不可控则限制量化结论。

## 15. 灰度、升级和回退

每项在临时数据库与项目中验收，完成后中文提交。正式升级前用 SQLite 在线备份或停服务完整备份，不能在运行中仅拷贝主库而忽略 WAL。

规则和观察策略先用于测试项目，再逐步开启。同轮修复由项目配置控制，先跑隔离样例再用真实项目。每次启用都能查看环境、规则和检查来源。

功能回退关闭策略并保留证据，数据库采用加法迁移，不删库回退。旧程序能否读取新库需用备份副本验证。设计阶段不重启在线服务；实施后按既有部署安排升级。

第一批的贯通验收是识别 mai_portal 规则和正确解释器、拒绝旧版本修改。第二批是“首次检查失败 → 同轮修复 → 重跑 → 一次最终回复”，缺环境时明确阻塞。之后根据真实回归结果再决定模型和 MCP 扩展。

### 第二批：持久检查、同轮修复和验收界面

检查存储已由 04999c3 交付。本批接入正常 Web 和 CLI 入口，在模型准备结束时执行检查；失败结果在同一回合反馈给模型，修复后重跑。所有检查走现有工具权限和停止流程，正式最终回复只生成一次。

- 每次执行保存命令、输入版本、解释器、开始和结束状态以及输出；历史 API 校验会话归属，完整输出按需分页读取。进程重启后未完成记录标为中断，不自动重做。
- 前端区分工作、检查、修复和收尾，当前检查与前次尝试放在同一展示框。刷新后读取持久记录，旧版变更卡继续兼容。
- 默认最多两次修复、六批检查、累计检查十分钟；每个检查仍受单项超时和模型原有预算约束。权限拒绝、停止、环境缺失和版本变化分别显示原因。
- Git 项目对改动文件的实际字节计算版本，二进制变化也能识别。非 Git 项目使用有数量和大小限制的文件清单，排除现有工具约定的生成目录；无法完整读取时标为受阻，不宣称通过。
- 检查中的代码或环境变化会使结果过期。通过只说明所运行命令在当时声明范围通过，不代表部署或外部服务已验证。

每个项目可以在 `.agents/project.json` 声明自己的检查，例如：

```json
{
  "schema_version": 1,
  "runtime": {"type": "python", "executable": ".venv/bin/python"},
  "checks": [
    {"id": "unit", "argv": ["{python}", "-m", "unittest", "discover", "-s", "tests"],
     "cwd": ".", "timeout_seconds": 300, "level": "unit"}
  ],
  "repair": {"enabled": true, "max_attempts": 2, "total_timeout_seconds": 600}
}
```

`argv` 按参数数组执行，只有 `{python}` 会替换为已选择的项目解释器；`cwd` 必须位于项目内部。省略 `checks` 时使用原有项目检查发现逻辑，空数组表示没有配置可运行检查。当前保守执行全部声明检查，尚未按路径裁剪。`repair.enabled=false` 仅关闭失败后的自动修复，仍执行和记录检查。
