# 自用体验与项目技能审查

审查日期：2026-11-03。基线提交：`4c65d1e 修复聊天消息重复乱序并优化界面与技能交互`。

本次完成源码审查与方案整理，未实施项目技能功能。现有业务数据库未修改。ZCode、DeepSeek Harness 使用本地源码；Claude Code 本机是安装包，结合其接口声明和官方文档核对公开行为。

## 结论

最值得先做的是让技能真正跟项目走。当前已有的界面、历史版本快照、发送时版本检查可以保留；需要补上项目发现、项目配置和统一解析。只给技能列表加“项目”筛选，不能保证实际执行时用对技能。

## 当前问题与优先级

### 1. 高：只有个人技能，没有项目技能归属

`backend/skills.py:12` 的根目录固定为 `data/skills/users/<uid>`；`backend/routes/skills.py:32` 的列表也只传用户 ID。列表、读取、保存、删除、发送解析都没有项目参数。

结果：不同项目会看到相同的技能库，不能让两个项目分别维护自己的 `code-review`。这是当前能力缺口，不是之前消息显示问题的复发。

修复方向：引入项目来源和稳定的技能引用键，前后端使用同一份项目目录解析结果。技能名称用于显示，不能继续独自承担全局身份。

### 2. 高：工作区与技能缺少统一的上下文切换边界

`frontend/app.js:2501` 的 `loadWorkspace()` 请求返回后直接改工作区标签，没有验证返回时是否仍在原会话。`chooseWorkspace()` 的异步返回也有同类问题。快速切换任务时，旧响应存在覆盖新任务标签的静态可达路径。

当前技能请求 `frontend/skills_view.js:65` 只检查用户和登录代次，不绑定项目或请求代次。直接在此基础上增加项目参数，会把竞态带进项目技能目录。

另一个接入点是 `backend/routes/sessions.py:79`：技能在新任务的工作区校验、绑定之前解析。增加项目技能后，应先确定有效工作区和会话归属，再解析技能；校验全部通过后再创建任务，避免无效目录留下空任务。

修复方向：统一的会话/项目上下文版本；工作区、技能目录、收藏、默认启用项随上下文一起切换；过期响应丢弃。同一会话改绑项目时也要处理原项目技能和排队消息。

### 3. 高：排队发送失败的恢复不完整

`frontend/app.js:5038` 派发时先移除并持久化队列，再发请求。失败路径 `frontend/app.js:5144` 只恢复文本和技能，未恢复 `payloadAtts` 到附件托盘；已有输入时也不会恢复文本。派发队列没有同步更新 `lastSent`。

结果：网络失败或技能版本不匹配时，队列里的原消息已经消失；附件和重试目标可能不完整。这对自用工具比更多视觉效果更值得优先修复。

修复方向：保留可恢复的发送项，明确区分待发送、提交中、提交失败；失败项可以完整重试或退回编辑，不覆盖用户新写的草稿。未知是否被服务端接收的请求还应结合 nonce 做幂等确认，不能盲目重发。

### 4. 中：收藏和固定使用的粒度不够

`frontend/skills_view.js:8` 按会话保存选择，`:9` 按用户保存收藏，均在 localStorage 中。项目 A 和 B 共用收藏；同一项目的新任务不会自动得到项目默认技能。

现有 `scope: once | session` 表示使用时长，不是技能归属。不能直接把它扩展成 `project | personal`，否则会破坏已有草稿和排队记录的含义。

修复方向：技能归属与使用时长分开建模。个人/项目是来源；本次/本会话是启用范围。“此项目默认启用”作为独立的项目偏好，按用户和项目保存到服务端。

### 5. 中：技能导入兼容性与问题提示不足

`backend/skills.py:29` 逐行拆分 frontmatter，并不是真正的 YAML 解析。本次在临时目录中验证：`description: |` 加两行简介，实际解析结果是字面量 `|`。前端导入器也使用类似的逐行处理。

`listing()` 遇到不可读、非法或过大的文件会直接跳过，用户看不到原因。目录中的 references、templates、scripts 也没有作为技能包管理；保存时只重写 name、description 和正文，其他 frontmatter 不保留。

修复方向：使用明确支持的格式解析，返回逐项诊断；保留可识别的元信息，对不支持的执行字段说明限制。先支持可靠的 SKILL.md，再补目录资源读取，避免把“成功导入文本”当成“完整兼容技能包”。

### 6. 中：目录刷新与保存存在额外请求和旧响应覆盖风险

输入 `$` 时每次输入都会调用 `openPicker()`，随后 `refresh()` 请求完整技能列表。列表包含每条技能的正文。慢的旧列表请求也可能在保存成功后返回，覆盖前端刚更新的目录。

`save()` 本身没有 expected-version 条件更新；两个编辑页面保存同一技能时，后保存者直接覆盖前者。文件写入使用原子替换，这一点应保留，但原子替换不等于编辑冲突检测。

修复方向：目录用轻量元数据，输入搜索在本地完成；详情按需读取；刷新带请求代次，保存带预期版本。初期采用进入项目、打开面板和手动刷新时更新即可，无需先引入复杂文件监听服务。

## 建议采用的最小方案

### 存储和身份

```text
个人技能：现有 data/skills/users/<uid>/<slug>/SKILL.md

项目 A/.agents/skills/code-review/SKILL.md
项目 A/.agents/skills/test/SKILL.md

项目 B/.agents/skills/code-review/SKILL.md
项目 B/.agents/skills/release/SKILL.md
```

项目技能文件可跟随 Git 管理。收藏、默认启用项、最近使用等个人偏好单独存数据库，不写进项目技能正文。

项目技能默认只看当前项目的根目录和必要的祖先范围，停止在项目边界，不扫描所有兄弟项目。首版兼容发现 `.claude/skills` 可以作为只读来源；遇到同名或不支持的字段时明确标注，复制到当前项目后再按本项目格式编辑。

本地项目偏好默认按规范化目录隔离。现有记忆的 `project_identity()` 会按 Git remote 合并克隆，不能不加区分地复用到技能偏好：同一个远程仓库的两个 checkout 可能有不同的技能文件和分支。目录搬迁、多个 worktree 是否共享偏好，后续提供显式选择。

技能引用至少区分 `来源 + 项目身份 + slug`，例如个人 `code-review` 与项目 A 的 `code-review` 是两条独立记录。保留原有个人技能引用的兼容映射。

### 使用方式

1. 选择项目后，优先展示“当前项目”，下面是“个人通用”。其他项目的技能不混进来。
2. 有项目时，新建技能默认保存到当前项目；没有项目时，默认个人技能。
3. 选择某技能后，仍可选本次或本会话使用；另有“设为此项目默认”，同项目新建任务会恢复默认项。
4. 同名技能默认使用当前项目版，并标记来源；个人版仍可明确选择，不能静默混用两份指令。
5. 收藏也按项目展示，并保留个人收藏。切项目时输入框、技能目录和默认项一起刷新。
6. “可用”不等于“全部启用”。首次不要把项目内所有技能正文塞进上下文。
7. 消息继续保存使用时的版本快照。技能改名、删除、更新都不改变旧消息回放。

### 实施顺序

第一批：修复工作区异步边界与失败消息恢复；引入项目技能发现、来源标记和统一服务端解析，前端按项目展示。

第二批：项目默认技能、项目收藏和复制个人技能到项目；旧个人技能与浏览器草稿兼容迁移。

第三批：标准 frontmatter、目录资源、外部目录导入和清晰诊断；根据实际技能数量再考虑缓存或文件监听。

暂不优先做技能市场、插件平台、全面自动触发或整个前端框架迁移。当前约 7500 行的 app.js 应围绕工作区状态和技能状态逐步拆分，避免同时重写聊天渲染和业务协议。

## 验收场景

- 项目 A/B 各有自己的同名代码审查技能，展示、选择、执行与回放都不会串。
- 项目 A 的默认技能在同项目的新任务恢复，项目 B 不继承。
- 新任务尚未创建时，预选项目也能看到项目技能；无效目录和无效技能不会生成空任务。
- 慢响应下从 A 切 B，再切 A，旧请求不能覆盖最后一次选择。
- 队列派发失败后，文本、附件、技能和目标项目都能完整恢复。
- 技能更新后，已发消息使用旧快照；未发送项提示版本差异，不静默替换。
- 个人与项目同名时，来源、默认解析结果和另一个版本都能看清。
- 多行简介、错误 frontmatter、缺失资源和权限问题都能给出可理解的提示。
- 子代理使用哪些项目规则和技能必须明确约定，不能假定主代理的 `_skill_context` 已自动继承。
