# 记忆 v2 设计：双层记忆（项目记忆 + 个人记忆）

> 状态：**设计待确认**，尚未动代码。

> 目标：在**保持并做好编码 agent** 的前提下，把记忆做对——项目记忆跟着项目，
> 个人记忆跟着人，两者都可见、可编辑、可随时间保持正确。

## 0. 问题一句话

当前只有**一个轴**（`type: user|feedback|project|reference`），它同时在回答两个
正交的问题：**这条记忆是说谁的**（who）和**在哪成立**（where）。一个枚举答不了
两个问题——所以"你偏好 pnpm"这条被写进了 `mai_portal` 的路径哈希桶，

- 打开 `coding-agent` 时**它不出现**（你的工作方式偏好丢了）
- 而 `coding-agent` 桶里 74 条中混着"这张表加了 *_txt 生成列"（这是**仓库事实**，
  不是你）

**根因不在提示词，在存储键里没有「你」。** 所以本设计的第一条不是改提示词，
是**把两个轴拆开**。

## 1. 数据模型

### 1.1 两个正交轴

```
owner   —— 这条记忆是关于【谁】的
          user    : 关于用户这个人（跨项目管理）
          project : 关于某个代码库/项目

scope   —— 它在【哪】成立（仅 project 层有意义）
          global  : 任何地方都成立（个人层的默认）
          repo    : 本仓库成立（项目层的默认）
```

`type` 保留（它仍有信息量：身份/偏好/纠正/事实/外部引用），但**降级为标签**，
不再承担"去哪一层"的职责。层由 `owner` 决定。

### 1.2 存储布局

```
data/memory/
├── users/
│   └── <user_id>/                     ← 个人层（一人一桶，永不随目录变）
│       ├── MEMORY.md                  ← 生成的索引（不再手维护）
│       └── *.md
└── projects/
    └── <project_id>/                  ← 项目层（一个项目一桶）
        ├── MEMORY.md
        ├── .project-id                ← 身份解析产物的落点（见 §2）
        └── *.md
```

**为什么个人层按 `user_id` 而不是 folder**：`users` 表已有主键，`sessions.user_id`
已经是归属维度。个人层直接挂它，一个用户一个桶，**换任何目录都在**。

**为什么项目层不按绝对路径**：见 §2。

### 1.3 frontmatter（新增字段）

```yaml
---
name: pnpm-not-npm
description: 用户偏好：包管理用 pnpm 不用 npm      # 索引行展示这一条
metadata:
  type: user            # 保留的标签轴：user|feedback|project|reference
  owner: user           # 新增：user | project      ← 决定去哪一层
  scope: global         # 新增：global | repo       ← 仅 project 层用
  updated: 2026-10-14   # 新增：ISO 日期，写入时由宿主盖章
  supersedes: old-slug  # 新增：可选，被本条目取代的条目
  sensitive: false      # 新增：可选，人工标记"永不注入"
---
```

**兼容性**：缺 `owner` → 按 §2.4 的推断规则判定，**不报错、不丢文件**；
缺 `updated` → 视为未知，不影响读取。这是"老库能直接跑"的保证。

### 1.4 索引行（格式不变，加日期）

```
- [pnpm-not-npm](pnpm-not-npm.md) — 用户偏好：包管理用 pnpm 不用 npm (2026-10-14)
```

日期让模型能判新旧——当前完全无从判断，这是"已作废条目还在被引用"的原因之一。

## 2. 项目身份：让记忆跟着项目走

### 2.1 三级解析器

```python
def project_identity(workspace) -> tuple[str, str]:
    """返回 (project_id, 来源)。来源用于 UI 提示"改名会不会丢记忆"。"""
    # 1) 显式标记文件（最稳，跟着目录走）
    #    <ws>/.agent-memory-id 或 <ws>/.git/agent-memory-id
    # 2) git remote（跨机器、跨 clone 稳定）
    #    git -C <ws> remote get-url origin → 规范化（去 .git / 去协议前缀）
    # 3) 回退：路径哈希（保持与现状一致）
    #    sha256(resolve(path))[:12]
```

### 2.2 为什么不能只认 git remote（实测数据）

| 事实 | 影响 |
|---|---|
| **34 个会话里 18 个 `workspace=None`** | 超过一半的会话根本没有项目——只认 remote 会让它们无处可去 |
| 真实用过 `/Users/meta/Downloads`、`/Users/meta/Postman`、`/Volumes/agent_usb` | **这些都不是 git 仓库**，remote 解析会失败 |
| `mai_portal` 有 **2 个 remote**（github + gitlab） | 只认 remote 会因"用哪个"而再次分裂 |

所以：**标记文件优先 → remote 次之 → 路径哈希兜底**，且**记录用了哪一级**。

### 2.3 UI 提示

若某项目走的是第 3 级（路径哈希），在项目设置里显式提示：

> ⚠ 本项目按路径识别。**重命名或移动目录会丢失项目记忆。**
> [写入标记文件，改为按项目识别]

一键写标记文件即可升级到第 1 级。

### 2.4 `owner` 推断规则（迁移老数据用）

```
1. frontmatter 已写 owner          → 用它
2. 文件名/描述命中"全局性"特征     → user
      · type=feedback（对工作方式的纠正，天然跨项目）
      · 描述含"用户偏好/用户要求/习惯/始终/永远/不要/喜欢"
      · 提到的是工具/风格/流程，而非本仓库的具体文件
3. 其余                            → project
```

**保守原则：拿不准判 `project`。** 判错的代价不对称——把项目事实误判成个人偏好，
会让它污染你在**所有**项目里的上下文；反之只是在这个项目里少一条。**爆炸半径小的
那个方向错。**

## 3. 分类：给模型的决策程序

当前契约只给了类型**定义**，没给**程序**——所以 74 条里的分类基本是掷骰子。
新契约要给可执行的判定顺序：

```
判断一条新信息该进哪一层：

Q1 它是在说【我这个人怎么工作】，还是在说【这个代码库怎么回事】？
    · 我这个人 → owner=user（个人层）
    · 这个代码库 → owner=project（项目层）

Q2 如果提到具体的文件/模块/函数/表/接口名 → 一定是 project
    （个人层不得引用本仓库的具体符号）

Q3 owner=user 的典型信号（任一命中即判 user）：
    · 用户对助手说话方式的要求（语言、语气、详略、要不要问）
    · 跨项目的工作习惯（先方案后代码、改完就提交、不要过度抽象）
    · 工具偏好（pnpm/node/python 版本/编辑器/提交信息风格）
    · 用户对助手本人的纠正（"别再这样"）

Q4 拿不准 → project

覆盖面检查（这些必须判对）：
     "我一直用 pnpm 不用 npm"            → user / global
     "这个仓库的测试要先设 DB_DSN"        → project / repo
     "别给我的代码加注释"                 → user / global
     "我们决定砍掉 Oracle 分支"           → project / repo
     "回答用中文"                         → user / global
     "这个仓库用 tab 不用 space"          → project / repo
```

### 3.1 feedback 类的强化

`feedback` 类型（用户对工作方式的纠正）**默认判 user**——它天然跨项目。
契约要求它带 `Why:` 和 `How to apply:` 两行（当前只是"要求"，执行器不校验；
本设计**在 `_validate_op` 里加校验**，缺了则拒收该条并在 `rejected` 里给原因）。

## 4. 注入：两条独立的块

### 4.1 组合方式

```python
def memory_blocks(user_id, workspace) -> str:
    personal = memory_index_block(memory_dir_for_user(user_id),
                                 heading="【个人记忆】关于你（跨项目持久）",
                                 max_lines=PERSONAL_MAX_LINES)   # 40
    project  = memory_index_block(memory_dir_for_project(workspace),
                                 heading="【项目记忆】本代码库",
                                 max_lines=PROJECT_MAX_LINES)    # 110
    return personal + project
```

**两块独立预算、独立截断**——个人层 40 行的上限永不因为项目层膨胀而被挤掉。
当前是单一 150 行预算，且按**插入顺序**截断（最早写入的最先被丢，而那往往是
最基础的个人偏好）。

### 4.2 前缀缓存不能破坏（硬约束）

`agent.py:630` 有一条明确不变式：**回合内 system 前缀逐字节不变**，否则供应商的
自动前缀缓存全灭。所以：

- 快照仍在**回合开始**取一次（`_memory_snapshot`），回合中途不刷新
- 个人层在**前**、项目层在后（越稳定的越靠前——个人层变化频率低于项目层）
- 顺序固定：`SYSTEM_PROMPT` → 个人块 → 项目块 → 时间块

⚠ **副作用（必须知情）**：模型在当前回合内用 `write_file` 写的新记忆，
**本回合看不到**（下一回合才生效）。这是现状的既有行为，设计保持不变。

### 4.3 token 成本量化

个人 40 行 + 项目 110 行 ≈ 150 行 ≈ 20–25K 字符。每轮重发全部历史，一个 40 轮的
回合意味着这份索引被发送 **40 次**。这是既有成本（当前单一索引已 74 行 / 13K 字符），
两层后略增。**上限是硬约束，不是参考值**——超了就先截项目层。

## 5. 冲突与优先级

两层都可能说同一件事。规则写进契约：

```
个人层管【怎么和你打交道】：语言、语气、详略、工作习惯、工具偏好
项目层管【这个代码库的事实】：构建/测试命令、架构决策、坑、约定

冲突时（如"总是 squash 提交" vs "本仓库保留历史"）：
  项目层在【本项目相关的事】上优先（它更具体）
  但不要静默选择——如实告诉用户"你的全局偏好是 X，本仓库约定是 Y，按 Y 处理"
```

可选的 `overrides: <slug>` 字段让项目条目显式声明"我覆盖某条个人偏好"，
使冲突可追溯。

## 6. 生命周期：让记忆随时间保持正确

### 6.1 写入

| 路径 | 谁写 | 目标层 |
|---|---|---|
| 模型回合内 `write_file` | 模型 | 按 `owner` 前缀路由（见 §6.3） |
| 轮末提取 | 提取器 | 提取输出里带 `owner`，宿主路由 |
| 用户在 UI 编辑 | 用户 | 直接写对应层 |

### 6.2 更新与取代

- **更新** = 同名 `write`（覆盖）——阶段 0 已统一口径
- **取代** = 写新条目 + `supersedes: <旧 slug>`，宿主**删除旧条目**并记日志
- **禁止**再把"（已作废）"写进描述行占着索引——当前 `docs-panel-left-position`
  就是这么残留在每轮 system 里的

### 6.3 模型读写路径（桥接）

模型通过 `.agent-memory/` 前缀读写（沙箱桥接，`code_tools.BRIDGE_MEMORY`）。
两层后需要区分，方案：**桥接根给两个前缀**

```
.agent-memory/          → 个人层目录（默认，兼容旧习惯）
.agent-memory/project/  → 项目层目录
```

⚠ 兼容风险：旧的 `_resolve` 桥接是**字面前缀**匹配。加子前缀要保证
`.agent-memory/xxx.md` 仍落在个人层（不能让老的写路径突然指向新位置）。
**这是本设计里最容易出错的一处，实现时要单独写用例。**

### 6.4 清理与 GC

- **启动时**：枚举 `data/memory/projects/*`，若某桶的 workspace 在 `sessions`
  里已无任何引用 → 标记 orphan（**不自动删**，UI 里可清理）
- **永远以 `sessions.workspace` 的真实取值枚举桶**，绝不 `iterdir()` 盲扫
  （阶段 0 已隔离的 81 个 fixture 桶就是盲扫的产物）

## 8. 迁移：现有 74 + 7 条怎么办

### 8.1 原则

**一个文件都不搬。** `owner` 缺省即为 `project`（§2.4 第 3 条），所以：

- `data/memory/0da85a6c44eb/`（74 条）→ 原地重命名为 `projects/<新 project_id>/`
- `data/memory/2f2bb23d1a49/`（7 条）→ 同上
- 个人层**初始为空**，由用户通过 UI 逐步把该提升的提上去

### 8.2 迁移步骤（幂等、可回滚）

```
1. 备份 data/memory → data/backups/memory-pre-v2-<ts>/
2. 用 sessions.workspace 的真实取值算出 project_id（走 §2.1 三级解析）
3. data/memory/<旧token>/ → data/memory/projects/<project_id>/
   （若目标已存在则合并索引行，不覆盖文件）
4. 对每条记忆跑 §2.4 推断，写回 owner 字段（只加字段，不改内容）
5. 建 data/memory/users/<user_id>/ 空目录
6. 写一个 migration 版本号，重复执行无副作用
```

### 8.3 那 18 个 `workspace=None` 的会话

它们没有项目。规则：**`workspace=None` 时只注入个人层**，项目层为空。
（当前这些会话读的是 `_FALLBACK_MEM_DIR` —— `data/memories/default/`，
实测该目录不存在，等于无记忆。）

### 8.4 已隔离的 81 个 fixture 桶

阶段 0 已移到 `/tmp/memory_fixture_quarantine/`。**确认阶段 1 迁移脚本用的是
`sessions.workspace` 枚举后即可删除**（它们不对应任何真实 workspace）。

## 10. 风险清单

| 风险 | 缓解 |
|---|---|
| **桥接子前缀破坏旧写路径** | 单独用例覆盖 `.agent-memory/x.md` 与 `.agent-memory/project/x.md`；迁移前先跑通 |
| **前缀缓存失效** | 快照仍在回合开始取；两块顺序固定；不改回合内刷新逻辑 |
| **误判 owner 污染所有项目** | 拿不准判 project；UI 提供"移动层"一键纠错 |
| **迁移损坏 74 条真实记忆** | 先备份；幂等；只加字段不改内容；目标是合并而非覆盖 |
| **个人层注入撑爆预算** | 硬上限 40 行，独立截断，且排在最前（不会被项目层挤掉） |
| **18 个 None-workspace 会话行为变化** | 明确规则：只注入个人层；写测试锁住 |

## 11. 分步落地建议

建议拆成三个可独立验证的小步，每步都能跑全量测试：

```
Step 1  数据模型 + 迁移（不动注入）
        · owner/scope 字段、三级身份解析、目录重排、迁移脚本
        · 验证：74+7 条完好、桶目录变成 projects/、重复执行无副作用

Step 2  双层注入（不动 UI）
        · memory_blocks()、双块拼接、桥接子前缀
        · 验证：个人层内容在任何目录都出现；项目层只在对应目录出现；
                前缀缓存不变式（快照只在回合开始取）

Step 3  UI + API（用户可操作）
        · /api/memory、记忆面板、移动层
        · 验证：能看、能改、能删、能移层
```

**建议先做 Step 1**——它风险最高（动真实数据）但收益最直接（改目录名不再失忆），
且验证方式客观（文件还在不在、条数对不对）。
