# coding-agent 对话与 Agent 交互开发方案

日期：2026-11-06。状态：用户已确认，按批次实施；第一批实现说明见文末。

## 1. 目标和边界

面向个人长期使用，让用户可以准确补充当前任务、引用具体内容、控制后续队列，并能检查实际交付结果。不同项目保持独立规则、环境、技能与工具配置。

借鉴 ZCode 的对话操作和变更审阅、DeepSeek Harness 的持久输入与结构化交互、mai_portal 的场景工具与产物衔接。不迁移三者整套框架，不为此改用 React，也不先增加一批 MCP 服务。

沿用已完成的项目规则和环境识别、读取版本保护、同轮验收修复、持久检查记录、进度提醒、压缩事实、会话/需求 ID，以及现有消息排序、权限和停止机制。项目设置保持在顶部，不再向输入区堆低频入口。

## 2. 当前基础与必须先解决的约束

- sessions.py 已有 nonce 提交回执和持久接收记录；turn.py 负责执行与结束。前端 outbox.js 保存未确认提交，queue_state.js 仍管理尚未发送的本地队列。
- 新队列必须复用这些接收和幂等能力，不能另起一套独立派发器。服务端负责已接受任务，前端只负责草稿和等待确认的提交。
- Agent 目前按完整回合接收用户输入。新增“补充当前任务”必须有独立的安全消费边界，不能在工具线程运行时改写模型历史。
- 项目与个人技能已有独立标识、默认选择和版本快照。新增发现能力不能覆盖手动选择或取消选择。
- 已有变更和检查卡。新增交付视图应在此整合，避免产生第二份相互矛盾的验证状态。

## 3. 目标交互

### 3.1 任务执行中的输入

空闲时维持现有发送方式。工作中，发送旁提供简短的投递选项：

| 操作 | 行为 | 界面反馈 |
| --- | --- | --- |
| 下一项任务，默认 | 当前回合结束后执行 | 已排队，可编辑、移除或调整顺序 |
| 补充当前任务 | 在下一个模型请求前纳入本轮 | 等待纳入 → 已纳入当前任务 |
| 停止 | 沿用停止按钮 | 停止已启动操作，未派发工具不再启动 |

首版不增加“强制抢占并自动重启命令”。用户补充“保留旧接口兼容”不会杀掉正在运行的测试，也不会自动重做可能有副作用的命令。

补充内容拥有自己的消息 ID，并关联原需求 ID。它不是第二个独立任务，也不能独立推进队列。历史可看到其纳入状态与所属需求，支持复制 ID。

若补充到达时回合已提交终态，服务端明确拒绝本轮纳入；前端保留原文并提供“作为下一项发送”，不静默改变用户的投递意图。断线只表示投递结果待确认，不代表任务已失败。

### 3.2 引用内容继续提问

选中回复文字，出现“引用提问”；文件变更中选择片段，出现“引用这段代码”。输入框上方显示可移除的引用标签。

引用记录消息 ID、原需求 ID、文字快照，代码引用额外记录项目、文件路径和行区间。首版只支持当前会话和项目，不做跨项目引用；引用不是执行权限，也不等于已读取当前文件版本。

第一版限制最多 5 条、合计 8KB UTF-8，超限明确提示缩小范围。大消息只取选中片段，不把整个工具输出重新塞入上下文。历史消息删除或截断后保留合法的引用快照，并标记原位置不可跳转，不能指向另一条消息。

### 3.3 结构化澄清

Agent 有真正的缺失信息时，使用问题卡：问题、少量选项、补充文字和提交按钮。回答后继续原任务，不要求复制选项到输入框。

不强制每次任务先问问题；不把方案讨论和权限授权混为一谈。选择某方案不授予 shell、数据库或外部服务的权限。

首版每次最多 3 个问题、每题最多 4 个建议选项，并支持自定义回答。问题独立持久化，刷新后可答，重复提交只接受一次。停止、回合结束或原问题已失效后，不把迟到答案注入别的任务；保留回答草稿，提示按新消息发送。

## 4. 服务端状态与执行设计

### 4.1 输入接收与队列

扩展现有回执和提交路径，统一校验用户归属、会话、项目、操作类型、nonce 和正文摘要。重复请求返回原结果；同一幂等键对应不同正文时返回冲突，不执行第二遍。

采用加法迁移，为已接受输入增加类型、目标需求、队列位置、版本与生命周期，必要时新增补充输入和问题记录表。草稿、接收、派发、消费各有明确状态，不用多份布尔值推测。

队列状态：queued → claimed → running → terminal；queued 可修改或取消，claimed 后锁定。编辑和排序使用预期版本校验，两个标签页冲突时刷新实际状态，不互相覆盖。

收敛为每个会话一个队列消费者，只在取得该会话执行槽位后 claim 下一项；不能先为每个提交启动一个线程并提前 claim，再依靠 Agent 锁等待。不同会话继续允许并行。队列项的项目身份固定，编辑正文不能顺带切换工作目录；技能、附件和引用随编辑形成新的有效版本。

原始提交及其回执保持不可变。修改已接受队列项是一条新操作，派发器读取其最新有效版本，不能通过改写旧 nonce 的请求正文破坏重试语义。

前端本地队列迁移时保留原 nonce，先向后端对账；收到接受确认才删除本地待确认记录。重连不会重新给同一条内容分配 ID 后再提交。

### 4.2 补充消费边界

补充状态：accepted → applied，或 rejected/expired。worker 在没有未完成工具调用、且尚未提交最终结果的边界，按服务端顺序消费补充。先持久记录纳入事实，再发布界面通知。

纳入后仍沿用原需求 ID、原预算、原权限。清除不再适用的候选收尾状态，按更新后的目标继续；需要重新检查时走现有 VerificationPolicy。

最终提交和补充接收必须在同一个生命周期控制下判断：最终候选生成后再检查是否有未消费补充，不能靠前端显示“正在处理”判断是否还能纳入。已进入终态后不重开旧回合。

进程崩溃后，尚未执行的普通队列可恢复等待；执行中的任务和已消费的补充不自动重做。对“纳入已记账但模型尚未请求”的状态显示中断，由用户决定继续，首版不承诺模型调用恰好一次。

### 4.3 问题等待边界

问题调用持久记录 request_id、所属需求、工具调用、问题正文、状态和答案。首次收到合法答案后进入 answered；用户停止进入 cancelled，服务重启进入 interrupted。所有状态更新校验原问题归属与版本。

首版在原回合内等待，复用取消和权限等待的唤醒机制，但数据与权限请求分开。等待时间、是否继续及界面状态由明确策略控制，不把超时当作用户同意。等待超过 15 分钟时中断该等待并清楚收尾，不自动选择默认答案。

## 5. 项目技能和工具配置

### 5.1 技能分两步推进

第一步只推荐，不自动启用。根据当前项目技能说明、项目类型和本轮需求给出少量推荐，说明来源和推荐原因；手动固定与手动取消选择优先。低频配置仍在项目设置和技能管理中。

第二步提供按需发现和加载：模型先看到有界目录，通过工具读取完整技能；不能根据技能摘要猜操作步骤。首版目录最多 30 项、单项说明最多 150 字，更多技能通过检索获取。

保留当前最多 6 个启用技能的限制；手动固定技能占用名额并锁定，不被自动替换。模型自动加载默认关闭，按项目单独开启。关闭或仅用户可调用的技能不进入模型目录。

项目技能使用现有 qualified ID，记录来源、内容哈希和实际加载时机。手动选择沿用发送时快照；按需加载核验目录版本，文件已变化则更新目录后重新选择，不能把旧摘要对应到新正文后不留记录。

### 5.2 项目工具组合

复用现有项目配置和工具白名单，先支持三个轻量组合：只读分析、正常开发、验证排错。根据项目技术栈和任务需要提供工具，不复制 mai_portal 的完整业务平台。

组合只决定能力可见性，最终执行仍经过权限闸门。切换不能使进行中任务获得未授权能力，也不新增绕过授权的快捷入口。MCP 按真实任务缺口逐个增加。

## 6. 统一交付视图

在现有回合变更与验收卡上增加统一摘要，不再新建并排的结果面板：

- 实际修改文件及单轮 diff，按需展开。
- 实际生成的文件与下载/打开入口，校验路径和会话归属。
- 实际运行的检查、状态、前次失败尝试和完整输出入口。
- 明确的未覆盖范围与阻塞原因；模型解释与宿主检查事实分别标识来源。

以持久检查表和真实变更记录为事实来源，不从最终回复中正则提取“已通过”。shell 生成但无法可靠确认的文件不猜成正式交付物；允许显式登记后校验。

旧历史没有新字段时继续显示现有卡片。模型最终答复保持自然，不强制所有问题都套固定模板。纯问答不显示空的文件与测试卡。

## 7. 接口和文件落点

接口名称为设计建议，实施时与当前路由注册方式对齐：

| 能力 | 建议接口/事件 | 主要文件 |
| --- | --- | --- |
| 持久队列及修改 | 会话 queue 查询；编辑、排序、取消带版本 | db.py、routes/sessions.py、services/turn.py、outbox.js、queue_state.js |
| 当前任务补充 | turn inputs 接收；input_accepted/input_applied/input_rejected | routes/sessions.py、agent.py、services/turn.py |
| 对话引用 | 提交 payload 的 references，服务端解析并校验 | blocks.js、render_blocks.js、小型引用模块 |
| 结构化问题 | questions 查询与 answer 提交；question_requested/question_resolved | 新增独立 question 服务、工具、前端问题卡 |
| 技能发现 | skills 目录/检索与模型加载工具；skill_loaded | skills.py、routes/skills.py、技能前端与 agent.py |
| 交付摘要 | 复用 checks 与变更；必要时增加产物查询 | snapshot.py、verification.py、turn_checks.js、render_blocks.js |

新事件保持现有 SSE 序号和回放语义，持久化之后才发送。事件过期后可由 API 恢复状态，不依赖内存 SSE 缓冲作为唯一记录。新模块按职责拆出，避免继续把状态和 DOM 逻辑全部追加到 app.js。

## 8. 开发顺序与提交范围

| 批次 | 内容 | 完成门槛 |
| --- | --- | --- |
| A | 服务端队列统一、编辑/移除/排序、前端对账 | 两标签页、刷新、断线和提交重试不会重复执行 |
| B | 补充当前任务与安全消费边界 | 补充能影响同轮后续行为；工具不中途重启；最终回复不重复 |
| C | 引用提问与代码片段引用 | 来源可跳转，重载可恢复，越权与超限被拒绝 |
| D | 结构化澄清卡 | 回答后继续原任务；停止、超时、迟到回答有明确状态 |
| E | 项目技能推荐，再按需加载与工具组合 | 手动选择优先、项目不串、加载版本可追查 |
| F | 整合交付卡和真实任务回归 | 卡片事实与执行记录一致，旧对话和纯问答不受影响 |

每批先补协议与验收说明，再开发、审查、测试，用中文独立提交。A/B 风险最高，不与界面重做混在同一个大提交。首版可先交付 A～D 使用，E 的自动加载作为后续单独开关开放。

预计 8～12 个有效开发日，包含状态迁移、集成和回归；这是工作量估计，不是完成日期承诺。

## 9. 验收和发布

必须保持：同一提交不重复执行；同轮只有一次正式最终回复；队列只在原有终态边界派发，补充和问题回答不能冒充 turn_end；停止后不派发新工具；失效检查不显示为当前版本通过。

新增回归重点：

1. Agent 调用工具时补充要求，下一次模型请求收到补充，已执行命令不被重做。
2. 补充与最终提交竞争、停止与问题回答竞争，结果只能落入一个合法状态。
3. 队列编辑、排序和取消与 worker claim 竞争，已派发项不可被改写。
4. 两标签页操作、网络重试、刷新、进程重启，不丢未确认内容、不重复派发。
5. 引用越权、旧消息删除、超大引用、混合附件和 XSS 内容。
6. 问题刷新后可答、重复提交幂等、超时或停止后不串入新任务。
7. 技能同名、文件修改、目录超限、手动取消、项目切换与加载预算。
8. 新旧历史、原文复制、ID 复制、图片标注、移动端 390px、草稿及原有检查修复。

除单测外，经正常 Web 入口跑隔离项目任务：纯问答、接口兼容修复、失败后修复、执行中纠正、澄清后继续、断线与停止。先以模拟模型证明状态行为，再固定真实模型、配置和起点重复运行至少 3 次；记录任务成功、重复副作用、无证据完成声明、耗时和模型用量。没有真实对照前不宣称成功率提升。

开发测试使用临时数据库和项目，不操作真实业务数据库。上线先备份 SQLite（包含 WAL 一致性），再按批升级。新功能逐项启用；回退关闭新增入口，保留持久记录，已接收待办暂停可见，不删除证据，也不自动重跑中断任务。

## 10. 第一批实施说明

本次交付 A 批：服务端持久队列、编辑/移除/上下移动、跨页面查询和本地 outbox 对账。

- 复用原提交回执和 nonce，增加 submission_queue（迁移 33～35）。原提交正文和摘要不随队列编辑改变；有效执行正文保存在队列中。
- 每会话一个消费者，在原会话执行锁内读取并认领最新队首。不同会话继续并行，后续项不会提前认领。编辑、排序和认领由数据库事务与 revision 决定，冲突返回409。
- 正文编辑保持附件、技能快照与项目不变。移除后保留回执，旧请求重试不复活任务。模型或项目在认领前发生变化时暂停并显示原因。
- 前端现有会话在工作中发送的新需求立即提交服务端；输入原文等 turn_start 才进入已执行时间线。本地仅保留未确认提交，先来的未确认内容会挡住本机后续本地提交。
- 查询只返回最长4000字符的轻量预览，不传图片正文或技能指令。编辑时按需读取完整正文，编辑上限64KB；超过上限的正文仍可执行，但不提供队列内编辑。每会话最多50项待执行需求。
- 重启后，未开始且未被暂停的队列可恢复；执行中断的输入保留供复制检查，后续项暂停，用户可明确继续。已落定的终态不因清理窗口崩溃被误认作执行中断。
- 已接受任务用“上移/下移”调整等待顺序；首版没有增加强制抢占当前命令的能力。执行中的任务不能编辑或取消为未执行，停止仍使用原按钮。
- SSE queue_changed 用于触发查询，持久状态才是事实来源；页面有低频补查以恢复丢失的通知。仍有会话/视图/登录状态校验，避免迟到响应串入其他项目。

本批未实施 B～F：当前任务补充、结构化引用、问题卡、技能按需加载及统一交付视图。浏览器场景用正常 Web/API 路径和隔离数据，执行消费者使用可控替身；尚未开展真实供应商模型的效果对照，也未重启线上服务或迁移实际用户库。

验证：后端全量866项、前端105项通过；队列交互、消息重放顺序、同轮验收、个人界面四组浏览器回归通过。另补测中断需求原文复制、移除记录后仍暂停后续任务，以及320px窄屏。测试夹具在切换临时数据库前等待后台消费者完全退出，最终全量运行没有遗留队列线程异常。
