# 对话异常收尾修复

问题链路：多项目上层目录被当作一个非 Git 项目计算检查指纹，触发读取上限；宿主要求重新总结，原答复被隐藏为候选；供应商返回 DSML 文本工具协议，被当作最终答复并记为正常完成。

修复：

- 上层目录缺少自身项目标志、而至少两个直接子目录包含项目标志时，识别为多项目容器。不扫描整个容器或推断统一测试命令，明确要求在具体项目分别验证。
- 检查范围无法确认时保留实际任务答复，并附自动验收受阻说明，不仅为改写宿主提示再次要求模型收尾。未执行的检查不标为通过。
- 拦截直接输出的 DSML/XML 工具调用及禁工具阶段的结构化调用。原文不转化为命令执行；最多补发一次禁工具的文字恢复请求。
- 文字恢复失败时，仅允许使用本轮仍有效、未被后续工具操作或用户补充作废的候选，显著标为未完成校验的草稿。无候选时显示未完成说明，不引用上一轮草稿。
- 恢复失败写入完成状态及回合错误；保留单一最终答复，后续队列按既有异常规则暂停。成功恢复正常记录，但携带恢复标记。刷新后从持久状态重建。
- 禁工具流在校验后展示；普通流以标记开头的内容暂存，避免拆分的工具协议先闪现为正文。代码围栏里的协议讲解仍可正常显示。

边界：本批没有自动修改既有会话历史，没有执行历史异常文本中的命令，也没有自动跨项目运行测试。多项目的独立验证方案仍需按项目配置；真实模型是否稳定输出自然语言不作保证，失败有明确兜底。

验证使用临时数据库、项目和正常登录入口；受控模型复现异常，不消耗真实模型额度。覆盖协议分片、一次恢复、连续失败、草稿保留、连接异常、停止、多项目容器、真实 Agent/HTTP/SSE、异常回合持久化、刷新和手机显示，并回归补充当前任务及引用提问。

最终结果：后端全量890项、前端105项通过；登录页面的异常收尾恢复及补充/引用两组场景通过。
